# Initial Admin Provisioning

Admin accounts cannot be created through public registration. An operator with access to the backend runtime and target MongoDB database creates the first admin using a one-off command.

## Prerequisites

Install dependencies with `npm ci`. Configure `MONGODB_URI` and `JWT_SECRET` as described in the repository README; the command validates the backend configuration and does not need the HTTP server running. Confirm that the connection points to the intended database before executing.

The database identity must be able to read and insert users and create the user indexes. Provisioning waits for the unique indexes before inserting anything.

## Local provisioning (PowerShell)

From the repository root, use a trusted terminal. This prompts for the password without echoing it and pipes the JSON through standard input instead of exposing it as a process argument:

```powershell
$initialAdminName = Read-Host 'Admin name'
$initialAdminEmail = Read-Host 'Admin email'
$initialAdminPassword = Read-Host 'Admin password' -AsSecureString
try {
  $initialAdminPayload = @{
    name = $initialAdminName
    email = $initialAdminEmail
    password = [System.Net.NetworkCredential]::new('', $initialAdminPassword).Password
  }
  $initialAdminPayload | ConvertTo-Json -Compress |
    npm run provision:admin -w backend -- --stdin
} finally {
  if ($initialAdminPayload) { $initialAdminPayload.password = $null }
  $initialAdminPassword.Dispose()
}
```

Use a unique password generated by a password manager: at least 12 characters, and at most 72 UTF-8 bytes. The input accepts only `name`, `email`, and `password`; the command assigns the admin role itself. Do not print, save, or log the plaintext payload. The password necessarily exists briefly in process memory.

A successful run exits 0 and reports that the initial admin was created. Failures exit nonzero without printing credentials, hashes, or database connection strings.

## Production provisioning

Run the same command as a restricted, manually initiated deployment job or from an authorized operations host. Inject `NODE_ENV=production`, `MONGODB_URI`, and `JWT_SECRET` through the deployment secret manager. Supply the three-field credential JSON from a protected secret mount or directly through the job's stdin.

For example, on a Linux production host with a secret-manager-mounted JSON file:

```sh
npm run provision:admin -w backend -- --stdin < /run/secrets/placementhub-initial-admin.json
```

The file must contain a single JSON object with `name`, `email`, and `password`. Restrict the mount to the provisioning job, disable command tracing/payload logging, and remove the temporary secret mount after the job. Keep the admin credential in the operator's password manager. Do not put it in the application image, repository, CI arguments, or a permanent application environment variable.

Do not run provisioning on normal server startup, every deployment, or through an HTTP route. Restrict who can invoke the job and record its success/failure through the deployment audit log without recording its input.

## Safety and reruns

- If an admin already exists, the command refuses to run.
- If the email belongs to any account, the command refuses to promote it or reset its password.
- The initial admin receives a hidden, immutable `bootstrapKey`. A sparse unique index on this field prevents concurrent provisioning commands from creating two initial admins, including on standalone MongoDB.
- Demoting that account leaves the marker intact, so bootstrap cannot silently become a promotion or recovery tool. Deleting the account removes its marker; account deletion is not a supported recovery workflow.
- No admin is created automatically, and there are no default admin credentials.
- Additional admins, password recovery, and admin management interfaces remain out of scope.

## Verify access

Sign in through the existing `/login` page with the new credentials. The existing `/admin/account` page verifies the frontend role guard; it is not a dashboard.

For server-side verification, call `GET /api/v1/admin/access` with `Authorization: Bearer <accessToken>` obtained from normal login. It returns `200 { "status": "ok", "role": "admin" }` only for a currently authenticated admin. Missing/invalid/revoked sessions return 401; student/recruiter accounts return 403. The route reads the current role from MongoDB rather than trusting the JWT role claim.

Run `npm test` and `npm run lint`. Provisioning tests use isolated temporary MongoDB, exercise the actual stdin command, and never create an admin in your configured Atlas database.
